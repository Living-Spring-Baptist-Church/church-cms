# Backend Standards

Applies to `supabase/` (Postgres: schema, RLS, functions, tests, seed, and edge functions in `supabase/functions`), `packages/db` (CLI and generated types) and `packages/providers` (adapters). Read `CLAUDE.md` first; this document adds the backend detail. Table definitions and API operations are specified in `docs/system-design.md`.

---

## 1. Layers

Our backend is the database plus a few edge functions. Each layer still has one job and never reaches past its neighbour.

| Layer | Where | Job |
|---|---|---|
| Contract | GraphQL schema generated by pg_graphql from the `public` schema | The only surface apps talk to. Changing it is an API change. |
| Business logic | Postgres functions in `public` (exposed) using helpers in `private` | Every write with a rule: validate, apply, return the result, in one transaction |
| Permissions | RLS policies + `private` role helpers | Decide who sees and changes each row. The final authority. |
| Data | Tables, constraints, enums in `public`; audit in `audit` | Shape and integrity of the data |
| Background jobs | `supabase/functions/<job>/` (Deno, TypeScript) | Scheduled and queued work: outbox, publishing, nightly checks |
| Integrations | `packages/providers` | The only place a vendor SDK is imported |

Schemas: `public` (exposed to GraphQL), `private` (helpers, never exposed), `audit` (the log, never writable by app roles). Nothing internal goes in `public`.

## 2. Folder structure

```
supabase/                     the Supabase CLI requires this layout; it has no setting to move migrations
  config.toml
  migrations/                 <timestamp>_<verb>_<object>.sql (created by the Supabase CLI)
  tests/<domain>/             <topic>.test.sql (pgTAP)
  seed.sql                    fake demo data only, fixed random seed
  functions/<job-name>/
    index.ts                  thin handler: parse, call the service, respond
    <job-name>.service.ts     the job's logic
    <job-name>.test.ts
packages/db/
  package.json                pinned Supabase CLI; the root pnpm db:* scripts run it
  types/                      generated TypeScript types (never edited by hand)
packages/providers/src/
  <capability>/               sms/, email/, payments/, monitoring/
    <capability>.types.ts     the interface (e.g. SmsProvider)
    outbox-<capability>.ts    free demo implementation
    <capability>.test.ts
```

Domain names match the frontend exactly: `members`, `attendance`, `content`, `finance`, `messaging`, `settings`, `audit`.

## 3. SQL naming

| Thing | Convention | Example |
|---|---|---|
| Tables | plural `snake_case` | `ledger_entries` |
| Columns | `snake_case`; booleans start `is_`/`has_`; timestamps end `_at`; dates end `_on` | `is_active`, `archived_at`, `occurred_on` |
| Foreign keys | `<singular>_id` | `member_id` |
| Enums | singular `snake_case` type, values `snake_case` | `member_status` : `'active'` |
| Write functions | `verb_noun` | `record_offering`, `reverse_ledger_entry` |
| Read functions | `get_<noun>` (one) / `list_<nouns>` (many) | `list_audit_log` |
| Function parameters | `p_` prefix | `p_member_id` |
| Local variables | `v_` prefix | `v_period` |
| Policies | `<table>_<action>_<who>` | `members_select_office` |
| Triggers | `<table>_<purpose>` | `members_updated_at`. The audit trigger is the one exception: `audit_<table>` (system design), e.g. `audit_members`. |
| Indexes | `<table>_<columns>_idx` | `ledger_entries_period_id_idx` |

With name inflection on, pg_graphql turns these into camelCase (`recordOffering`, `amountMinor`). Never hand-camelCase in SQL.

## 4. Tables

Every table, in the migration that creates it:

- `id uuid primary key default gen_random_uuid()` (pg_graphql requires a primary key)
- `created_at` and `updated_at timestamptz` (trigger-maintained); `archived_at` instead of DELETE
- `not null`, `check`, `unique` and foreign key constraints wherever the domain requires them. The database rejects invalid data even if every app has a bug.
- Money as `amount_minor bigint` + `currency char(3)`, with `check (amount_minor > 0)` and a `direction` where relevant
- `alter table ... enable row level security;` plus explicit policies for each role in the PRD permission matrix
- The audit trigger: `create trigger audit_<table> after insert or update or delete on public.<table> for each row execute function audit.record_change();` then `alter table public.<table> enable always trigger audit_<table>;` so `session_replication_role = replica` cannot skip it
- A single `id` column even on link tables and one-row-per-parent tables (for example `member_departments` with `unique (member_id, department_id)`, and `attendance_counts` with `unique (service_id)`; the same applies to `attendance_checkins` and `program_participants`): `audit.record_change()` reads `id` from the row, so a composite primary key without `id` cannot be audited
- Relationship names in GraphQL: every foreign key gets a `comment on constraint ... is e'@graphql({"foreign_name": "...", "local_name": "..."})'`. The `foreign_name` must differ from the inflected name of the foreign key column itself (`assigned_to` is `assignedTo`, so its relationship is `assignedStaff`), otherwise both fields share a name. List every field of the type in a pgTAP test to catch it.
- Indexes on every foreign key and on columns used in common filters
- `comment on table` and `comment on column` for anything exposed. These become the GraphQL API documentation.

## 5. Functions (the business logic)

- One function, one business operation. At most 80 lines; split helpers into `private`.
- **Validate first**, then act. Reject bad input with a coded error (§7) before touching data.
- Runs in one transaction (a function call already is one). Return the created or changed row so the client can refresh.
- `security invoker` by default, so RLS still applies. `security definer` only when truly needed, always with `set search_path = ''`, fully qualified names, and a one-line comment saying why.
- Mark `stable` for reads (exposed as GraphQL queries) and `volatile` for writes (exposed as mutations). Getting this wrong puts the operation in the wrong place in the API.
- When a function owns a business rule, the table's direct GraphQL insert/update is blocked by RLS so the function is the only path.
- **Set-based SQL, no N+1.** Never loop over rows issuing a query per row. Use joins, `insert ... select`, `update ... from`, or `= any(p_ids)`.
- pg_graphql exposes parameters with their `p_` prefix (`pServiceId`, `pMen`), so the frontend calls `recordAttendanceCounts(pServiceId: ...)`. A function that returns a set (`setof`) is run more than once by pg_graphql, which breaks any write: a mutation returns one row (`returns public.<table>`) or a scalar such as a count, never a set.
- pg_graphql silently drops a function that has an enum parameter, so it never appears in the schema: take `text` and cast inside, or fix the value in the function (`register_child` always creates an active child).
- A write function that nobody may reach through the table (no insert or update grant, as for `attendance_counts`) is the only write path, so its role check is the gate: check the role first, then validate, then look the record up.
- No dynamic SQL. If ever unavoidable, only with `format('%I', ...)` / `%L`, never string concatenation.
- A SQL function body is resolved when it runs, so a helper that a `CHECK` constraint calls and that itself calls another `private` function must be `security definer` (with `set search_path = ''`): the writing role has no USAGE on `private`. A constraint that calls a `private` function directly needs only EXECUTE on it (see `max_headcount`).
- A status flow is defined once in a `private` function that returns the next status or raises (`private.next_content_status`), and a `before update of status` trigger refuses any other move, so no path can skip a step or bring an archived item back. Columns only a workflow may write (`status`, `approved_by`) have no column grant for app roles, and the function is `security definer` with the role check first.

## 6. No magic values in SQL

- No unexplained numbers or repeated literals inside functions and policies.
- Fixed values that are part of the rules (age of majority, maximum page size, minor units per currency unit) are immutable functions in `private`, e.g. `private.age_of_majority()`, so they have one definition and a name.
- Values the church may change (service times, expense categories, departments) live in data (`settings`, `lookup_values`), never in code.
- Status values are enums, never free text compared as strings.

## 7. Errors

One consistent error shape, so the frontend's single error handler can map every failure.

```sql
raise exception using
  errcode = 'P0001',
  message = 'FINANCE_PERIOD_CLOSED',            -- stable code, SCREAMING_SNAKE_CASE, DOMAIN_REASON
  detail  = format('Period %s is closed', v_period.month),  -- technical detail for logs
  hint    = 'Record the correction in the current month';   -- optional
```

- `message` is always a stable error code from the catalogue below, never a sentence. The frontend maps codes to plain text in `core/errors/error-messages.data.ts`.
- Add every new code to the catalogue in the same change, and its message to the frontend map.
- Never leak another member's data in `detail`.

| Code | Meaning |
|---|---|
| `AUTH_FORBIDDEN` | Role not allowed to perform this action |
| `VALIDATION_FAILED` | Input failed a check (details name the field) |
| `NOT_FOUND` | Record missing or not visible to this user |
| `FINANCE_PERIOD_CLOSED` | Insert into a closed or approved month |
| `FINANCE_SELF_APPROVAL` | Approver is the requester |
| `FINANCE_SAME_COUNTER` | Second cash counter is the first counter |
| `FINANCE_ALREADY_REVERSED` | Ledger entry was already reversed |
| `CONTENT_NOT_APPROVED` | Publishing an item that a pastor or super admin has not approved, by a role that cannot approve (`publish_content`, `publish_sermon`) |
| `STAFF_LAST_SUPER_ADMIN` | Change would leave the system with no active super admin |
| `STAFF_INACTIVE` | Target staff member is deactivated (for example granting them a role) |
| `STAFF_ROLE_ALREADY_GRANTED` | Staff member already holds this role (for this department) |
| `AUDIT_LOG_IMMUTABLE` | Someone tried to update, delete or truncate `audit.log` (never reaches a user in normal use; map to the generic error message) |

## 8. Security

- Least privilege: revoke default privileges on each schema from `anon` and `authenticated`, then grant only what each needs. `anon` can read published content and nothing else.
- The public read rule (LBC-33, first anon-readable data): `anon` gets column level `SELECT` on the public columns only (never author, approver, status or timestamps), and one policy per table: `status = 'published' and publish_at <= now()` (and `expires_at is null or expires_at > now()` where the table has it). `now()` is the transaction time, so scheduling and expiry take effect at once with no job, and a null `publish_at` is never visible. A scheduled item is `published` with a future `publish_at`: there is no `scheduled` status. A `CHECK` requires `publish_at` and `approved_by` on every published row. Tests prove each hidden state, the boundaries at `now()` and that the session time zone changes nothing. Any new anon grant needs this same treatment and a test of every hidden column, relationship, filter and ordering.
- Every policy is tested from both sides: the allowed role succeeds, every other role is denied.
- Two-factor is enforced in the database (LBC-41). `private.has_role`, `has_any_role` and `heads_department` count a role in `private.mfa_required_roles()` (super admin, pastor, treasurer) as held only when the JWT claim `aal` is exactly `aal2`; anything else, including a missing or malformed claim, fails closed. The list must equal `MFA_REQUIRED_ROLES` in `apps/dashboard/src/core/auth/roles.ts`; a pgTAP test pins it, change both together. Never read `staff_roles` for the caller's roles outside these helpers, or the rule is bypassed. `private.is_active_staff()` ignores `aal` on purpose and may gate only the own-profile reads (`staff_select_self`, `staff_roles_select_self`) that the login flow needs at aal1; never use it to grant business data. Anything that must also work for staff with no role (the audit event writer) uses `private.has_dashboard_session()`.
- Tests that act as a signed-in user put `aal` in the claims: `'aal', 'aal2'` for ordinary role tests (every existing suite does), `'aal', 'aal1'` to prove the denial. The matrix for every role at both levels lives in `supabase/tests/mfa/`.
- Children's records (under the age of majority, LBC-42): visible to super admin and pastor (archived included), to heads of a children's ministry department for the non-archived children of the department they head, and to the secretary for the children of any department flagged `is_childrens_ministry` (option d: she is treated like a children's ministry head; never youth or other minors). `private.is_minor(date_of_birth, adult_confirmed)` decides: a known date of birth wins; with none the person is an adult only when `adult_confirmed` is true, so unknown ages are hidden. Only super admin and secretary can set `adult_confirmed` (trigger `members_guard_adult_confirmed`). A child is created only through `register_child` (member and department link in one transaction, no orphan); direct inserts of minors stay super admin only; removing a minor's children's ministry link is super admin only. Households: the secretary sees one when it is empty or holds someone she may see. Tables that follow member visibility (check-ins, program participants, follow-ups, department links) therefore show the secretary the children of the ministry too. Ushers and the treasurer never read minors, also not in `member_names`.
- A view that exposes part of a protected table to roles with no policy on it (`member_names`) runs with its owner's rights, so it must check the caller's role inside its own `where`, be created `with (security_barrier = true)` so a caller's condition cannot leak filtered rows through an error message, be granted to `authenticated` only, and carry the `@graphql({"primary_key_columns": [...]})` comment to appear in GraphQL.
- The service role key lives only in edge function secrets. It never appears in either Next.js app, in Git, or in logs.
- Input from users is validated in the function even though the frontend validated it too.

## 9. Migrations

- Create with `supabase migration new <verb>_<object>` (for example `create_members`, `add_is_minor_to_members`). One logical change per file.
- A migration that creates a table includes, in the same file: constraints, indexes, RLS, policies, audit trigger, grants and comments.
- Once a migration has run anywhere outside your own machine, it is immutable. Fix forward with a new one.
- Destructive changes (dropping a column or table) happen in a separate, later migration after confirming nothing uses it, never bundled with the change that stops using it.
- `supabase db reset` must apply every migration plus seed from zero, cleanly, every time.
- After any schema change: regenerate TypeScript types and the GraphQL schema, and commit them in the same PR.
- Seed data is fake, deterministic, and never contains real people.

## 10. Testing (pgTAP and edge functions)

- One test file per domain topic: `supabase/tests/finance/ledger-reversal.test.sql`. Cross-cutting schema checks live in `supabase/tests/structure/`.
- Descriptions read as BDD: `'should reject an offering when the period is closed'`.
- Tests run as a specific role by setting the JWT claims helper, never as the database owner, so RLS is really exercised.
- A setup statement in a test file must not print a result that looks like a TAP line (`ok 1`): wrap it in a `void` helper. A refused statement is asserted through a helper that returns `<sqlstate> <message>`, so the exact failure is checked, not just that something failed.
- Every policy: allowed and denied cases for each role touched.
- Every finance rule: the success case and every failure case (closed period, self-approval, same counter, double reversal, deposit not counted as income).
- A structural test fails if any `public` table lacks RLS, policies or a complete audit trigger (row-level AFTER INSERT OR UPDATE OR DELETE running `audit.record_change()`, enabled for normal sessions). It is `supabase/tests/structure/public-tables-security.test.sql`. `audit.log` immutability (UPDATE, DELETE and TRUNCATE refused for every role) is tested in `supabase/tests/audit/`.
- Edge functions and providers: Vitest-style tests with the same rules as the frontend (colocated, BDD names, 80% coverage, no real network).

## 11. Edge functions and providers

- Handler (`index.ts`) is thin: parse and validate input with Zod, call the service, return a response. No logic in the handler.
- Jobs are idempotent: running twice never sends a message twice or double-publishes. Use row status transitions (`queued` to `sent`) guarded in SQL.
- Database jobs (pg_cron, extension created with `create extension if not exists pg_cron with schema pg_catalog`): the logic is a plain function in `private` that returns a count, with no execute grant to any app role, so pgTAP can run it directly; the migration then calls `cron.schedule('<job-name>', '<schedule>', 'select private.<function>()')`, which updates the job of that name instead of adding a second. The job name and schedule are `private` constants. The job runs as the migration owner with no signed-in user, so its audit rows have a null `actor_id`. Visibility rules never depend on a job: a job only keeps stored statuses truthful (`private.archive_expired_content`). The test checks the `cron.job` row (name, schedule, command, user) and runs the stored command.
- Batch reads and writes; never one query per row.
- Providers: one interface per capability, one free demo implementation that writes to the outbox or logs, and a test. A real vendor implementation is added only after the church approves the cost, recorded in an ADR.

## 12. Logging and observability

- Edge functions log structured JSON with a level, a request ID, the operation name and non-sensitive context. No `console.log` debugging left behind.
- Never log tokens, keys, phone numbers, emails, amounts tied to named members, or anything about children.
- The audit log records business changes; it is not an application log and is never used for debugging output.

## 13. Environment variables

Every variable is listed in `.env.example` with a dummy value and validated at startup (Zod in the apps, `Deno.env` checks in functions). Current set:

```
NEXT_PUBLIC_SUPABASE_URL        public project URL
NEXT_PUBLIC_SUPABASE_ANON_KEY   public anonymous key (safe in the browser; RLS protects data)
SUPABASE_SERVICE_ROLE_KEY       edge functions only, never in the apps
APP_ENV                         local | staging | production
SENTRY_DSN                      optional, error tracking
```

## Backend checklist

- [ ] Change is in the right layer (contract, function, policy, table, job, provider)
- [ ] New tables: primary key, timestamps, constraints, indexes, RLS, policies, audit trigger, grants, comments
- [ ] Business writes are functions: validate first, one transaction, return the row, correct `stable`/`volatile`
- [ ] Set-based SQL, no N+1, no dynamic SQL
- [ ] No magic numbers or repeated literals; enums for statuses
- [ ] Errors raise a catalogued code; frontend message map updated
- [ ] Least-privilege grants; service role key only in edge functions
- [ ] Migration is new (not edited), one logical change, applies from zero; destructive changes separate
- [ ] Types and GraphQL schema regenerated and committed
- [ ] pgTAP tests with BDD names cover allowed and denied roles and every failure case
- [ ] No secrets or personal data in code, seed or logs
